# Захват кадров GL/GLES без изображения 0×0

30 октября 2026 года. Изменены библиотеки `gl` и Granio, их проверки и
документация. Приложения не менялись. Минимальный Go — 1.27.1, проверки — Go 1.27.2.

## Причина и воспроизведение

Win32 при сворачивании передаёт `WM_SIZE/SIZE_MINIMIZED` с размером 0×0.
GLFW доставляет нулевые размеры окна и framebuffer. `processResized` записывал
их в логический размер canvas, затем захват создавал изображение 0×0.
Кодировщик PNG не принимает такое изображение.

Дефект воспроизведён двумя native-тестами: точным callback `resized(..., 0, 0)`
и настоящим `Iconify()` собственного окна Windows. Исходный код в обоих случаях
давал canvas 0×0 вместо 80×60:
[исходная ошибка](gl-capture-validation/baseline-zero-windows.log).

Одного сохранения размера оказалось недостаточно. После минимального
исправления back buffer свёрнутого окна возвращал чёрный пиксель вместо зелёного:
[промежуточная проверка](gl-capture-validation/geometry-fixed-windows.log).
Поэтому захват теперь заново рисует canvas в независимый framebuffer.

Это доказанный путь возникновения пустого кадра в библиотеке. В первоначальном
однократном сбое EXE из предыдущего этапа состояние native-окна не записывалось;
приписать именно тому запуску `WM_SIZE` задним числом нельзя.

## Исправление в Granio

- Нулевые native-размеры сохраняют последнюю рабочую геометрию canvas.
  Положительный resize обновляет её; первый следующий снимок использует новый размер.
  Расчёт framebuffer scale защищён от нулевого делителя и невалидного масштаба.
- Native-захват рисует в полный временный RGBA8 texture FBO, затем читает пиксели.
  Он работает для готового скрытого окна до первого `Show/SwapBuffers` и для
  свёрнутого окна. FBO и текстура удаляются после операции; постоянного GPU-буфера
  снимка нет, обычный цикл отрисовки не выполняет дополнительных запросов состояния.
- Сохраняются отдельные read/draw FBO, viewport, pixel-pack/unpack layout и
  привязки PACK/UNPACK PBO. Свежая CPU-текстура не использует оставленный другим
  GL-кодом PBO. Ошибка этого сценария до исправления:
  [GL_INVALID_OPERATION](gl-capture-validation/unpack-fresh-windows.log).
  Это не обещание сохранять произвольное shader/blend/texture-состояние стороннего
  рендерера: его повторную настройку по-прежнему выполняет владелец draw-pass.
- Операция синхронно передаётся потоку контекста, в том числе при вызове из worker
  с тегом `migrated_fynedo`. Таблица функций принадлежит конкретному painter,
  сбрасывается при `Init` и не зависит от повторной загрузки глобальной таблицы.
- Backdrop-режим сохраняет premultiplied alpha; обычный снимок остаётся непрозрачным.
  `At` вне bounds и вложенный `SubImage` больше не выходят за границы пикселей.

Опциональный интерфейс `driver/desktop.CanvasCapture` возвращает
`CaptureWithError() (image.Image, error)`. Успех означает непустое изображение
положительного размера. Для ещё не созданного или закрытого native-окна
возвращается `desktop.ErrCaptureUnavailable`; ошибки размеров, FBO и чтения
также передаются вызывающему коду. Прежний `Canvas.Capture()` использует тот же
путь, при ошибке пишет её в журнал и возвращает `nil`.

Если GL 2.1 не поддерживает texture FBO, сохранён путь чтения рабочего native
drawable. Слишком маленькая или приостановленная поверхность возвращает ошибку.
Подставного изображения 1×1 и ранее сохранённого кадра нет. Этот fallback не
проверен на оборудовании без FBO. Мобильные/WebGL-адаптеры сохраняют прежний
способ чтения с проверкой размеров; native FBO-код в их сборку не входит.

## Изменения в gl

Новый пакет [`readback`](https://github.com/Uzer007-admin/gl/tree/dev/granio/readback)
проверяет `GLsizei`, координаты, объём RGBA8 и длину Go-буфера до чтения.
Он временно устанавливает плотную pixel-pack раскладку, отвязывает PACK PBO и
восстанавливает состояние при успехе, ошибке и panic. Повторное успешное чтение
с готовым буфером не выделяет Go-память — это проверено `AllocsPerRun`.

Параметры выбираются по фактическому API/версии/расширениям. Базовые ES 2 и
WebGL 1 не получают недопустимых запросов row-length/PBO. Отдельно учитываются
[NV_pack_subimage](https://registry.khronos.org/OpenGL/extensions/NV/NV_pack_subimage.txt),
[NV_pixel_buffer_object](https://registry.khronos.org/OpenGL/extensions/NV/NV_pixel_buffer_object.txt)
и desktop EXT/ARB PBO. Профиль `material` получил `PixelStorei` и enum чтения;
в нём 79 процедур, компактный профиль рендерера по-прежнему содержит 51.

Обёртки получены существующим Glow из декларации профиля. Повторная генерация
и gofmt дали идентичные байты девяти проверяемых файлов:
[generation-identity.json](gl-capture-validation/generation-identity.json).
Код генератора и GLFW в этом этапе не менялся.

## Короткие проверки

| Среда | API и исполнитель | Результат native-набора с race |
| --- | --- | --- |
| Windows | OpenGL 4.6, NVIDIA RTX 4080 SUPER, драйвер 616.92 | 7/7 |
| X11 / Xvfb | OpenGL 4.5, Mesa 25.0.5, llvmpipe | 6/6 |
| X11 / Xvfb | настоящий контекст GLES 2.0, Mesa, llvmpipe | 5/5 |
| Wayland / Weston 10.0.1 headless | OpenGL 4.5, Mesa, llvmpipe | 6/6 |
| Wayland / Weston 10.0.1 headless | настоящий контекст GLES 2.0, Mesa, llvmpipe | 5/5 |

Во всех Linux-наборах проверены нулевое уведомление и следующий положительный
resize, пиксели скрытого первого кадра, alpha, закрытое окно, вложенные контексты
и восстановление FBO/viewport/pack/unpack после загрузки новой CPU-текстуры.
Windows дополнительно проверяет реальное сворачивание. Desktop GL также
проверяет сохранность таблиц двух painter после неудачного глобального reload.
GLES 2 запущен с `MESA_GLES_VERSION_OVERRIDE=2.0`; фактическая версия записана в
журнал, это не подмена GLES desktop-контекстом.

На Windows и Linux также прошли наборы `readback`, `material`, `capabilities`,
`v2.1/material`, `v2.1/fyne`, `v2.0/gles2` и проверки painter/desktop с race.
WebAssembly-версия painter собрана; запуск в браузере не выполнялся.
Итоги, команды и журналы: [checks.json](gl-capture-validation/checks.json).

Байты 19 изменённых исходных Go-файлов и деклараций сверены между Windows и
Linux: [source-identity.json](gl-capture-validation/source-identity.json).
Из-за недоступного DNS Linux использовал vendor из отдельного workspace без
изменений настроек стенда. Weston запускался только для этой проверки.
В опубликованных журналах заменены локальные абсолютные пути; диагностические
сообщения и результаты сохранены.

## Опубликованные версии

```sh
go get github.com/Uzer007-admin/granio/v2@v2.8.2-0.20261030092632-a80862403af9
```

Granio закрепляет `gl v0.0.0-20261030092416-83550b6a7fd2`. Данные коммитов и
проверки публикации: [versions.json](gl-capture-validation/versions.json).

Отдельный короткий EXE собран с этими опубликованными модулями,
`GOWORK=off` и без `replace`. Публичный `CaptureWithError` вызывается из worker
для показанного, свёрнутого через Win32 `ShowWindow` и восстановленного окна.
Во всех трёх состояниях проверены центр кадра, native-признак сворачивания и
успешная запись PNG 320×240. PNG побайтово совпали:
[published-runtime.json](gl-capture-validation/published-runtime.json),
[снимок свёрнутого окна](gl-capture-validation/minimized.png).

Первая проба предполагала неизменный размер маленького окна 83×61 после
восстановления; фактический валидный снимок был 120×61. Проверка фиксированного
размера поэтому использует 320×240. Геометрия маленьких окон не подменяется
заданным размером снимка.

## Границы приёмки

На Windows проверен один NVIDIA-драйвер. Xvfb и headless Weston с llvmpipe
проверяют native-протоколы, контексты и содержимое кадров, но не заменяют
физические Intel/AMD, GNOME, KDE, Fly, mixed-DPI и аппаратную смену мониторов.
Windows/GLES, macOS и мобильные runtime в этом этапе не проверялись.
Длительные performance-проверки не выполнялись, количественный выигрыш CPU
или времени GPU по этим функциональным проверкам не заявляется.
