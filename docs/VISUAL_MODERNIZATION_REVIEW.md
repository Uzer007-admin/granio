# Кроссплатформенное развитие визуальной системы

Обновление 14 октября 2026: текущие API, проверки и открытые аппаратные пункты
сведены в [VISUAL_MODERNIZATION_COMPLETION.md](VISUAL_MODERNIZATION_COMPLETION.md).
Нижеследующая оценка сохраняет контекст первоначального архитектурного разбора.

Исходные пожелания: `Fyne_Visual_Modernization_TZ.md`, версия 1.0 от 11 октября
2026 года. Этот документ изучен как предложение. Его требования, ограничения
платформ и критерии завершения не приняты автоматически.

## Что полезно сохранить

Тема должна улучшать существующие виджеты, сохранять виртуализацию и данные при
смене оформления. Нужны точные дробные координаты, независимое увеличение текста,
контрастные состояния и фокус, ограниченные кэши и ресурсы эффектов. Геометрия
caret, IME, hit testing, clipboard/drop и accessibility должна использовать одну
систему координат. Глобальный прозрачный фон не является материалом окна.

## Что требуется переработать

- Исходный документ закрепляет Fyne 2.8.1. Рабочий форк основан на `7f99a87b`
  ветки develop, поэтому имена API и поведение сверяются с текущими исходниками.
- Качественный непрозрачный интерфейс, текст, ввод и доступность — общий результат
  Windows, Linux и macOS. Нативный material — возможность конкретного backend.
  DWM не задаёт архитектуру общего painter и не определяет качество Linux.
- Тема и density не должны копировать Windows-контролы. Системные предпочтения
  следует читать адаптерами ОС, сохраняя явный выбор приложения. High contrast,
  reduced motion и запрет прозрачности требуют независимой политики.
- HDR, широкую гамму и прозрачную поверхность нельзя подразумевать из разрешения
  дисплея. Нужна отдельная диагностика формата и цветового пространства.
- Требования на 60 Гц заменяются измерениями по целевой частоте. Проверяются
  60, 120, 144, 160, 180, 240, 280, 300 и 360 Гц. Частота callbacks, CPU preparation,
  GPU duration, present intervals и input-to-present фиксируются отдельно.
- Под названием 2K проверяются DCI 2048×1080 и распространённый QHD 2560×1440;
  4K — 3840×2160; 5K — 5120×2880. Это размеры framebuffer. Нативные координаты
  окна, логические размеры Fyne и плотность framebuffer различаются.
- Полный набор всех пересечений из документа чрезмерен. Автоматизируются чистые
  преобразования и протоколы, затем выполняются критические аппаратные сочетания.
  Проверка на Xvfb/Weston подтверждает native backend, но не физический дисплей.

## Бюджеты кадров и ресурсов

| Частота, Гц | Период кадра, мс |
| --- | --- |
| 120 | 8.333 |
| 144 | 6.944 |
| 160 | 6.250 |
| 180 | 5.556 |
| 240 | 4.167 |
| 280 | 3.571 |
| 300 | 3.333 |
| 360 | 2.778 |

Это общий период, а не разрешённое время одной функции. GPU/vsync и дорогая сцена
могут снижать фактическую частоту. После пропуска периода не выполняется серия
устаревших кадров. При простое нет постоянной перерисовки; ввод пробуждает loop.

RGBA8 для 4K занимает 31.64 MiB, для 5K — 56.25 MiB. Три полных поверхности 5K
занимают 168.75 MiB без depth/stencil, MSAA и текстовых атласов. Поэтому 64 MiB
для blur нельзя трактовать как бюджет полного окна. Эффект должен работать с
областью панели, учитывать временные поверхности, reuse при resize и уменьшение
разрешения фильтра. Рабочую поверхность и незаменимые текстуры нельзя молча
выкидывать из учёта.

## Уже реализуемая общая основа

`theme.NewModern(theme.ModernOptions{...})` — переносимая opt-in opaque-тема:
light/dark определяются существующим ThemeVariant; HighContrast включается явно;
TextScale меняет типографику, Density — внутренние отступы. Системные шрифты
и vector icons используют существующие механизмы Fyne. Выбранный accent получает
контрастный foreground. HighContrast можно включить явно; системный high contrast
также применяется к modern-профилю. `FollowSystem` подключает системный accent и
text scale при отсутствии явных значений. Windows provider и семантическая палитра
описаны в [SYSTEM_APPEARANCE_VALIDATION.md](SYSTEM_APPEARANCE_VALIDATION.md).

`desktop.ScalableWindow` предоставляет ScaleLegacyRounded и ScaleExact.
ScaleInfo показывает system/user/effective/framebuffer scales. Exact сохраняет
125% и 175%; legacy остаётся исходным профилем. На Windows content-scale callback
теперь обрабатывается также при смене DPI неподвижного окна. HWND и WM_DPICHANGED
по-прежнему принадлежат GLFW: второго обработчика suggested rectangle нет.

Переносимая тема используется независимо от native-материалов. Выполненные
Windows/Linux window-visuals и appearance-проверки фиксируются отдельно в
`WINDOW_VISUALS_VALIDATION.md`, `LINUX_WINDOW_VISUALS_VALIDATION.md` и
`SYSTEM_APPEARANCE_VALIDATION.md`. Полная аппаратная приёмка ТЗ этими блоками
не завершается.

## Последовательность дальнейшей визуальной части

1. Проверить gallery opaque-профиля, клавиатуру, IME, контраст, text scale и DPI
   на каждой ОС; сохранять состояние виджетов при live-переключениях.
2. Добавить общий снимок system appearance и capability flags с адаптерами
   Windows, Linux portals/settings и macOS; подписки отменяются при завершении.
3. Зафиксировать per-window surface/alpha policy и бюджет GPU. Исследовать
   прозрачную композицию каждого desktop backend с реальным GPU.
4. Подключать нативные window materials и общий in-canvas blur независимо.
   Unsupported или fallback — диагностируемое состояние. Без аппаратной проверки
   не объявлять вызов API доказательством видимого материала.

## Основания для нативных контрактов

- [ITextStoreACP](https://learn.microsoft.com/en-us/windows/win32/api/textstor/nn-textstor-itextstoreacp)
  и [RECONVERTSTRING](https://learn.microsoft.com/en-us/windows/win32/api/imm/ns-imm-reconvertstring):
  ACP/length в UTF-16 units, offsets reconversion в bytes.
- [UIA Text attributes](https://learn.microsoft.com/en-us/windows/win32/winauto/uiauto-textattribute-ids)
  и официальные SDK headers: поддерживаемые patterns и типы значений.
- [AT-SPI](https://github.com/GNOME/at-spi2-core/tree/main/xml): text, value,
  selection, table и события на отдельном accessibility bus.

Результаты выполненных проверок фиксируются отдельно от этой архитектурной оценки.
