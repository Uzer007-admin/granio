# Подвисание видео и рабочего стола при запуске OpenGL

31 октября 2026 года. Для этого стенда подтверждены программный обход и
аппаратный вывод OpenGL через DXGI. Внутренняя причина неисправности старого
пути представления WGL в связке видеодрайвера и DWM пока не установлена.

## Аппаратный OpenGL с выводом через DXGI

После пересборки с новой библиотекой совместимые непрозрачные окна Windows
выбирают DXGI автоматически. Выбор проверяет фактические возможности текущего
контекста и успешное создание аппаратного устройства D3D11. Если interop
недоступен, сохраняется WGL. Кода приложения для этого менять не требуется.

Для явного выбора режима:

```powershell
$env:GRANIO_WGL_PRESENT = 'dxgi'
& .\приложение.exe
```

`auto` или отсутствие переменной — автоматический выбор; `wgl` — прежний
путь через `SwapBuffers`. `GRANIO_RENDERER=software` имеет приоритет над
этими значениями и остаётся отдельным программным режимом.

Приложение должно быть пересобрано с новой библиотекой. Контекст WGL,
шейдеры и отрисовка OpenGL остаются аппаратными. Готовый задний буфер
копируется внутри GPU в D3D11-текстуру через `WGL_NV_DX_interop2`, после чего
кадр передаётся Windows через DXGI flip model. В рабочем цикле нет чтения
кадра в память CPU и вызова WGL `SwapBuffers`. Нужны desktop OpenGL,
`WGL_NV_DX_interop2` и совместимое аппаратное устройство D3D11.
Основание механизма: спецификации
[Khronos](https://registry.khronos.org/OpenGL/extensions/NV/WGL_NV_DX_interop2.txt)
и [Microsoft](https://learn.microsoft.com/en-us/windows/win32/direct3ddxgi/dxgi-flip-model).

В 23-секундном запуске копии того же приложения пользователь подтвердил
исчезновение подвисаний рабочего стола и видео. Журнал подтвердил аппаратный
interop и два кадра 1180×800 перед простоем. В отдельной 23-секундной пробе
непрерывного обновления DXGI выбирался автоматически, без сборщика и
вспомогательных окон. Проба завершилась штатно: 1379 успешных представлений
1180×800. Пользователь также подтвердил отсутствие подвисаний рабочего
стола и видео. Исходные файлы приложения не изменялись.

Нативный тест проверил первый кадр, порядок RGBA и вертикальную ориентацию,
изменение размера, захват canvas, нулевой кадр, восстановление scissor и
read buffer, освобождение ресурсов. Он прошёл и с `-race`. Добавлены проверки
автоматического выбора, сохранения подготовленного alpha-окна на WGL,
аппаратного предела размеров и восстановления после подменённого ответа
`DXGI_ERROR_DEVICE_REMOVED`. Последняя проверка пересоздаёт реальные ресурсы
interop; настоящего сброса видеокарты в ней нет. Восстановление ограничено
одной попыткой до следующего успешного кадра и не зацикливается при отказе.
Полноразмерный первый кадр готовится перед показом окна. Пять прежних
Windows-проверок GL также прошли с `-race`. На Linux прошли по четыре
проверки GL и GLES для X11 и Wayland. Linux использовал Mesa llvmpipe;
это регрессия библиотек, а не аппаратная приёмка Linux.

Полная короткая проверка копии приложения также прошла в автоматическом
режиме: расчёты, кодировки, экспорт, снимки интерфейса и простой. Журнал
подтвердил аппаратный interop и 140 кадров 1180×800. Это функциональная
проверка; она не заменяет наблюдение за видео и рабочим столом.
[Состав проверок и контрольные суммы исходников](windows-desktop-stall-validation/wgl-dxgi-checks.json).

Этот вариант DXGI непрозрачен. В режиме `auto` окна с заранее подготовленным
alpha остаются на WGL/DWM, сохраняя существующий механизм Mica, Acrylic и
прозрачности. Поздний запрос alpha для непрозрачного автоматического окна
по-прежнему требует пересоздания. При принудительном `dxgi` для Mica,
Mica Alt, Acrylic, Transparent и SystemBlur публикуется непрозрачный fallback;
этот результат отдельно проверяется через WindowVisuals. GLES использует
прежний путь вывода. Аппаратная приёмка прозрачного пути через DXGI требует
отдельной реализации DirectComposition; эта версия её не заявляет.

## Рабочий обход в библиотеке

В Windows можно явно выбрать оконную программную отрисовку:

```powershell
$env:GRANIO_RENDERER = 'software'
& .\приложение.exe
```

EXE должен быть пересобран с версией Granio, содержащей этот режим. Менять
прикладной код не требуется. Значение действует в текущем процессе PowerShell
и его новых дочерних процессах. Для возврата к обычному GL-режиму:

```powershell
Remove-Item Env:\GRANIO_RENDERER
```

Окна сохраняют драйвер ввода GLFW, создаются с `GLFW_NO_API` и выводят
программный кадр через GDI. WGL-контекст не создаётся. В проверочной копии того
же приложения не загружались NVIDIA OpenGL ICD и компилятор шейдеров;
системная `opengl32.dll` остаётся импортом существующих GL-обёрток.
Кадр переиспользуется до изменения размеров, передаётся GDI без второй копии
всего изображения и рисуется только при изменениях. Захват возвращает свою
копию пикселей; для закрытого, свёрнутого или нулевого окна возвращается
`ErrCaptureUnavailable`.

В 25-секундной записи этого режима DWM выдавал события в течение всей записи:
4919 кадров, максимальный наблюдаемый интервал изменения изображения 27,75 мс.
Для независимого D3D11-окна получено 1499 представлений и 3 пропуска;
максимальный интервал — 58,33 мс. Это одна короткая проверка, а не норматив
производительности. Пользователь сообщил об исчезновении постоянного
подвисания. Отдельный повторный запуск без повышения прав и сборщика ETW
также прошёл без замеченной пользователем паузы при старте.

Режим предназначен для обхода проблем аппаратного OpenGL. CPU рисует кадр;
GLSL-шейдеры не выполняются. WindowVisuals использует непрозрачный fallback
для Mica, Acrylic, Transparent и SystemBlur. Аппаратный GL/GLES остаётся
режимом по умолчанию; параметры драйвера при выборе software не меняются.

## Что проверено

Исходный симптом — при открытии Granio-окна затормаживаются также видео,
рабочий стол и другие приложения. Успешный ответ очереди Granio за доли
миллисекунды не проверяет задержки представления кадров других процессов.
Системный режим перемещения `SC_MOVE` — отдельный сценарий; его пауза не
объясняет зависание рабочего стола при обычном запуске без перемещения.

В короткой минимальной пробе с GLFW без Granio и прикладных виджетов:

| Операция | Один измеренный запуск |
| --- | --- |
| `glfw.Init`, вариант без GL | 12,6 мс |
| Создание окна `GLFW_NO_API` | 3,5 мс |
| `glfw.Init`, вариант WGL | 8,9 мс |
| Создание окна с WGL/OpenGL | 645,4 мс |
| `Show` WGL-окна | 10,2 мс |

Среда — Windows 11 build 26300, NVIDIA RTX 4080 SUPER, драйвер 616.92.
GLFW — `5c267d637d9d`, GL — `83550b6a7fd2`.
Данные первого запуска: [noapi.jsonl](windows-desktop-stall-validation/noapi.jsonl),
[wgl.jsonl](windows-desktop-stall-validation/wgl.jsonl).
Повторная проба с `QueryPerformanceCounter`:
[noapi-qpc.jsonl](windows-desktop-stall-validation/noapi-qpc.jsonl),
[wgl-qpc.jsonl](windows-desktop-stall-validation/wgl-qpc.jsonl).
Её исходники: [wgl-startup-probe](../scripts/wgl-startup-probe/README.md).

Это локализует существенную часть времени запуска в ветке создания WGL,
которая присутствует и без Granio. Замер не устанавливает причину торможения
других процессов. Это одна короткая проба без статистической приёмки.

В свежем WGL-окне фактически получен swap interval 1. Интервалы 0 и 1
переключаются. Первый Go-таймер записал короткие вызовы `SwapBuffers` как 0.
Повторный замер через QPC дал 0,034–0,137 мс при исходном интервале 1,
0,035–0,052 мс при интервале 0 и 0,038–0,049 мс при явном интервале 1.
Создание WGL заняло 670 мс, обычного окна — 2,7 мс. Это время возврата API,
а не физического отображения. Утверждение о зависании внутри `SwapBuffers`
по этому набору не подтверждается. Значение по умолчанию описано в
[WGL_EXT_swap_control](https://registry.khronos.org/OpenGL/extensions/EXT/WGL_EXT_swap_control.txt).

Диспетчер Granio на Windows пока не задаёт swap interval явно. Само это
наблюдение не доказывает связь с общесистемным подвисанием. Настройки драйвера,
композитора и приложений в ходе этой проверки не изменялись.

## Полученная системная трасса

Для разделения создания контекста, работы OpenGL ICD, задержек DWM,
планировщика и сторонних модулей подготовлен
[`record-windows-graphics.ps1`](../scripts/record-windows-graphics.ps1).
Он собирает 20 секунд GPU/CPU ETW и счётчики выбранного процесса. Приложение
запускает пользователь после начала записи. Скрипт не запускает и не закрывает
приложения, не меняет драйвер или его настройки, не отправляет данные в сеть.
Каждая запись использует уникальное имя WPR; остановка адресована только ему.
Существующий каталог результата не перезаписывается.

WPR не смог начать запись из имеющегося процесса: `0xc5585011`,
`Failed to enable the policy to profile system performance`. В его токене
отсутствует `SeSystemProfilePrivilege`. Это ограничение записи, а не результат
диагностики GPU. После подтверждения повышения прав получены короткие
GPU/CPU-трассы длительностью 25 секунд.

Первый подробный профиль потерял 51 175 событий и не захватил нужный процесс;
его нельзя использовать для приёмки. Повторные записи с облегчённым профилем
захватили процесс, сохранили трассу и не потеряли событий или буферов.
Профиль исключает сбор каждого системного вызова и GPU-стеков, сохраняя
CPU-стеки, переключения потоков, GPU-планирование и представление кадров.
Исходник: [windows-graphics-light.wprp](../scripts/windows-graphics-light.wprp).

В одной записи исходного приложения получено 85 отсчётов процесса:
около 2,125 секунды CPU за 22,627 секунды наблюдения и максимум 192,7 МиБ
рабочего набора. Эти величины не объясняют общесистемное подвисание сами по себе.
Непрерывная перегрузка CPU или длительные DPC/ISR в этой записи не установлены.
Перезапуск видеодрайвера по событиям Display/nvlddmkm в проверенном интервале
также не зафиксирован. Это не исключает дефект драйвера или композитора.

## Сравнения и исключённые обходы

| Проверка | Полученный результат |
| --- | --- |
| Самостоятельное окно GLFW/OpenGL без Granio | Нет доказательства устранения |
| Win32/WGL на C++, без Go, GLFW и Granio | Пользователь подтвердил подвисание рабочего стола и видео |
| Swap interval 0 вместо 1 | Устранение не подтверждено |
| Сохранение текущего контекста вместо detach | Устранение не подтверждено |
| Один буфер, `GL_FRONT`, `glFlush` | Нет доказательства устранения |
| DWM Alpha с успешным `DwmEnableBlurBehindWindow` | Пользователь подтвердил сохранение подвисания |
| `DwmFlush` до или после вывода | Поток счётчиков восстановился, но приложение получило дополнительные паузы; исправлением не принят |
| NVIDIA Prefer native для отдельного тестового EXE | Параметр прочитан обратно как 0, пользователь подтвердил сохранение подвисания |
| Временно отключённый NVIDIA Overlay | Пользователь подтвердил сохранение подвисания; исходное состояние оверлея восстановлено |
| `glFinish` перед обычным `SwapBuffers` | Аппаратная проба завершилась штатно, пользователь подтвердил сохранение подвисания рабочего стола и видео |
| Аппаратный OpenGL/WGL с представлением DXGI в копии приложения | Пользователь подтвердил отсутствие подвисаний в простое и при 23 секундах непрерывного обновления; второй запуск прошёл без сборщика и вспомогательных окон |

Последняя проверка использовала разрешённый временный профиль NVIDIA,
связанный только с отдельным диагностическим EXE. После проверки профиль
удалён, отсутствие привязки приложения проверено повторным чтением.
Число профилей вернулось с 7984 к 7983; прочитанные глобальные и базовые
параметры совпали с исходными. Профили пользовательских приложений,
MPO, HAGS, VSync и параметры восстановления драйвера не изменялись.

Отдельная разрешённая проверка оверлея использовала неизменённую Win32/WGL-пробу.
Оверлей был выключен только на время проверки и затем включён обратно.
Модуль `nvspcap64.dll` загружался и при выключенной функции. Само наличие
модуля не устанавливает активность захвата или причину неисправности.
Принудительное завершение GPU-команд через `glFinish` также не принято
как исправление: успешное завершение 665 кадров аппаратной пробы не совпало
с устранением видимого пользователю дефекта.

## Ограничения измерения кадров

PresentMon 2.6.0 в части записей выдаёт события только для первых 4–13 секунд
25-секундного сбора, хотя сборщик успешно завершает работу, а ETW не сообщает
потерь. Разрывы этой выдачи нельзя объявлять измеренной длительностью
физического зависания экрана. Microsoft отдельно указывает, что при Hardware
Flip Queue обновление статистики кадров может требовать `DwmFlush`:
[GetFrameStatistics](https://learn.microsoft.com/en-us/windows/win32/api/dxgi/nf-dxgi-idxgiswapchain-getframestatistics).
Видимый дефект независимо подтверждён пользователем; восстановление выдачи
счётчиков при `DwmFlush` не доказывает его устранение.

Чтение NVAPI `GetAdaptiveSyncData` в отдельных WGL-пробах также переставало
обновлять время последнего flip. Счётчик может не описывать используемый
устаревший путь представления WGL; его возраст нельзя выдавать за измеренную
паузу рабочего стола. Возврат `SwapBuffers`, отдельного DXGI-окна и счётчиков
других процессов проверяет разные части вывода и требует сопоставления
с наблюдаемым симптомом.

Точная внутренняя причина на стороне видеодрайвера или композитора пока
не установлена. Аппаратный DXGI-вариант внесён в оконный драйвер Granio с
автоматическим выбором для совместимых непрозрачных окон. Проверенные
отрицательные переключения не внесены
в обычную ветку WGL.
Полные ETL и списки процессов сохраняются локально и не публикуются.

## Повторение записи

Проверка команды без записи и повышения прав:

```powershell
.\scripts\record-windows-graphics.ps1 -ValidateOnly
```

Для записи откройте PowerShell от имени администратора и выполните:

```powershell
.\scripts\record-windows-graphics.ps1 -Seconds 20 -ProcessName 'granio-app' -ProfilePath .\scripts\windows-graphics-light.wprp
```

После сообщения о начале записи запустите именно проблемную Granio-сборку.
Вместо `granio-app` передайте имя её EXE без `.exe` в `ProcessName`.
Фактические зависимости можно проверить `go version -m путь-к-программе.exe`:
имя файла само по себе не подтверждает использование Granio/OpenGL.
Во время проверки запуска не перемещайте и не закрывайте окно. Через 20 секунд
трасса будет сохранена в новый каталог `graphics-trace-*` в корне репозитория,
независимо от текущего каталога PowerShell.
Результаты: `graphics.etl`, `capture.json`, `process-samples.json` и журналы WPR.
Проверяйте `trace_saved: true` и `process_seen: true`; наличие одного каталога
не подтверждает запись и запуск нужного процесса.
Скрипт не повышает права самостоятельно. Если остановка WPR не удалась,
журнал содержит имя собственного сеанса для восстановления.
Имя также записывается в `capture.json` до начала записи. В таком случае из
PowerShell администратора остановите только этот экземпляр:

```powershell
wpr -stop путь-к-результату\graphics.etl -skipPdbGen -instancename имя-из-capture.json
```

WPR записывает системные и прикладные ETW-события, которые анализируются в WPA:
[документация Microsoft](https://learn.microsoft.com/en-us/windows-hardware/test/wpt/windows-performance-recorder).
Запись с правами администратора проверена. Устранение подвисания подтверждено
для простоя и непрерывного обновления на RTX 4080 SUPER. Приёмка других
GPU, версий Windows и прозрачного пути WGL/DWM остаётся открытой.
Длительных performance-прогонов на этом этапе нет.
