# Событийное обновление частоты мониторов

30 октября 2026 года. Минимальный Go — 1.27.1; проверки выполнены Go 1.27.2.

## Исправление

Ранее настольный цикл в `internal/driver/glfw/loop_desktop.go` каждые две
секунды обходил все подключённые мониторы и запрашивал текущий видеорежим,
даже когда приложение простаивало. `SetFrameRate(60)` отключал этот обход,
но обходным решением приходилось пользоваться каждому приложению отдельно.

Периодический опрос удалён. Автоматический режим получает начальный снимок
частот и обновляет его по уведомлениям ОС. Пачка уведомлений объединяется
одним атомарным флагом; чтение режимов выполняется после обработки событий,
без повторного входа из native callback. Простой не вызывает новых запросов.

Фиксированный режим по-прежнему пропускает запросы частоты. Возврат к нулевой
частоте запрашивает свежий снимок; повторный `SetFrameRate(0)` позволяет явно
обновить кеш. Существующий минимум автоматического режима 60 Гц сохранён,
верхняя граница ограничена 1000 Гц, как и публичный фиксированный режим.
После отключения быстрого монитора кешированная частота может уменьшаться.

## GLFW

В модуле `github.com/Uzer007-admin/glfw/v3.5/glfw` добавлено расширение форка
`SetMonitorConfigurationCallback(func())`. Стандартный `SetMonitorCallback`
по-прежнему сообщает только о подключении и отключении монитора.

| Backend | Источник уведомлений |
| --- | --- |
| Win32 | `WM_DISPLAYCHANGE` собственного служебного окна GLFW |
| X11 | RandR output/CRTC notifications; добавлена подписка на смену CRTC |
| Wayland | Завершённая пачка `wl_output.done`, подключение/удаление output |
| macOS | `applicationDidChangeScreenParameters`, подключение/отключение |

Callback вызывается на потоке событий GLFW. Он только помечает данные как
устаревшие. При `Terminate` снимается регистрация и освобождается Go-ссылка
на callback. Повторная инициализация проверена. Исходный проект GLFW:
[go-gl/glfw](https://github.com/go-gl/glfw); это добавление локального форка.

## Проверки

- Политика кеша: 10 000 проходов без события дают один первоначальный запрос;
  пачка событий — один дополнительный. Проверены отключение быстрого монитора,
  фиксированная частота, возврат к автоматической, границы и нулевые выделения
  памяти на пути без событий.
- Windows: native `WM_DISPLAYCHANGE` направлялся только собственному helper
  текущего потока, без смены видеорежима и без broadcast другим приложениям.
  Проверены доставка, замена/снятие callback и освобождение при завершении.
- Windows и Linux/X11: целевые native-тесты драйвера с race, включая анимации
  120–360 Гц и немедленное пробуждение из простоя.
- Linux: GLFW собран со всеми включёнными backend; lifecycle уведомлений и
  создание native-поверхности проверены на Xvfb и собственном Weston 10.0.1.
  Wayland/GLES-драйвер прошёл тот же целевой набор с race.
- Windows: регрессионные проверки GLFW-драйвера, desktop API и галереи
  в программном режиме отрисовки.

Байты 19 изменённых Go/C/Objective-C файлов сверены между Windows и Linux:
[source-identity.json](monitor-events-validation/source-identity.json).
Итоги и журналы: [checks.json](monitor-events-validation/checks.json).
DNS стенда был недоступен; финальные Linux-проверки использовали автономный
vendor из отдельного временного workspace без изменений настроек стенда.

## Проверка EXE

Для проверки сделан отдельный снимок приложения-потребителя. Его интерфейс
и данные одинаковы в контрольной и исправленной сборке; файлы исходного
приложения не менялись. Проверочная команда явно выбирала `SetFrameRate(0)`,
включая сценарий возврата с фиксированных 60 Гц.

Оба шестисекундных прогона завершились с кодом 0, выбрали 360 Гц и дали
побайтово одинаковый PNG 1180×800. Go heap после принудительного GC —
25 265 456 и 25 276 304 байт; CPU-время всего процесса — 1,797 и 1,953 с.
Это короткая проверка совместимости; количественный выигрыш CPU/памяти ею
не установлен. Снижение памяти от ленивого создания страниц приложения
не приписывается изменению драйвера. Данные:
[exe-comparison.json](monitor-events-validation/exe-comparison.json).

Дополнительно потребитель собран через опубликованные Go-модули при
`GOWORK=off`, без локальных `replace`. В первом запуске опубликованного EXE
снимок имел размер 0×0 и проверочная команда завершилась с ошибкой PNG.
Диагностический запуск показал canvas 1180×800, scale 1; повторный запуск
того же исходного EXE также завершился успешно. Оба последующих кадра
совпали с контрольным. На том этапе причина первого пустого кадра не была
установлена и OpenGL-рендерер не менялся. В следующем этапе воспроизведены
нулевое native-уведомление и захват свёрнутого окна, исправлены геометрия и
GL/GLES-захват: [исправление пустого кадра](GL_CAPTURE_REPAIR.md).
Состояние окна в первоначальном запуске не записано, поэтому точная причина
того единичного события остаётся неподтверждённой.
Данные и первоначальная ошибка сохранены:
[published-runtime.json](monitor-events-validation/published-runtime.json),
[published-initial-error.log](monitor-events-validation/published-initial-error.log).

## Границы проверки

Физическое переключение режима/горячее подключение монитора не выполнялось.
На Windows проверен настоящий обработчик сообщения без изменения оборудования;
снижение частоты после отключения проверено тестом политики кеша.
Wayland проверен на headless Weston, X11 — на Xvfb; это не аппаратная приёмка
в GNOME/KDE/Fly. Код macOS обновлён, запуска на macOS не было. Длительные
performance-проверки не выполнялись. Один короткий профиль cgo не используется
как доказательство CPU-ускорения или устранения всех возможных зависаний ОС.
